# 必须满足条件（硬门槛）与评分推荐衔接设计

日期：2026-10-07
适用模块：`src/core/condition-service.ts`、`src/core/analysis-service.ts`、`src/ui/components/ConditionsPanel.vue`、`ResultPanel.vue`

## 1. 要解决的问题

原有比较只输出加权后悔总分，任何维度的优点都可能抵消另一维度的严重不足。但现实中存在“不能被抵消”的要求，例如：

- 可逆性不能低于 60%（决策一旦做出无法回头，再好的成长也不能补偿）；
- 某项影响不能低于指定值，例如“金钱影响不能为负”；
- 反之也可能要求上限，例如“短期收入波动不高于 +2 档”。

这些条件与评分是**两道独立闸门**：评分回答“在可选项中谁更好”，门槛回答“谁有资格被选”。高分不能购买资格。

## 2. 条件模型

每条条件 `MustCondition`：

| 字段 | 含义 |
| --- | --- |
| `metric` | `stability / growth / freedom / money`（影响 −5～+5）或 `reversibility`（0～100） |
| `operator` | `gte`（不低于，下限）或 `lte`（不高于，上限） |
| `threshold` | 阈值，受指标取值域约束 |
| `tolerance` | 边界容忍带，默认 0；实际值落在阈值 ±tolerance 内判“尚无法判断” |
| `enabled` | 单条开关；另有全局开关 `conditions.enabled` 一键关闭整套门槛 |

条件随案例持久化（localStorage），结果中以“本次计算依据”原样回显，保证报告可复核。

## 3. 三值判断：满足 / 不满足 / 尚无法判断

对单方案 × 单条件，判断结果只能是三种：

| 状态 | 判定（以 `gte` 为例，`lte` 对称） | 语义 |
| --- | --- | --- |
| `pass` | actual ≥ threshold + tolerance | 明确达标 |
| `fail` | actual < threshold − tolerance | **有明确事实且明确越过边界** |
| `unknown` | 实际值为 `null`（未评估），或 \|actual − threshold\| ≤ tolerance | **尚无法判断，不记为不满足** |

“不满足”与“尚无法判断”必须区分，二者导向完全不同的行动：

- **数据缺失 → unknown**：影响值允许显式标记为“未评估”（null），与明确给出的 0（中性影响）不同。缺失不被当作 0 分或失败，而是要求补数据。
- **贴近边界 → unknown**：当输入是主观估计（滑块值）时，59 与 60 的差异不具有信息意义。容忍带承认这种测量误差，避免用伪精确把方案一棍子打死。容忍带默认为 0（严格阈值），由用户按数据可信度调大。
- 判断理由同时输出 `actual` 与 `margin`（距阈值余量），结果页逐条展示“实际值—阈值—差距—结论”。

### 3.1 方案资格三档

- `eligible`：全部启用条件 `pass` —— 具备选择资格；
- `conditional`：没有 `fail`，但至少一条 `unknown` —— **条件候选**，可查看与追踪，暂不能被推荐；
- `excluded`：任一 `fail` —— 明确不满足，总分仅供对照，永不被推荐。

## 4. 条件冲突与配置错误

分两类处理，不混为一谈：

1. **条件之间互相矛盾（分析期冲突）**：同一指标的“不低于 a”严格高于“不高于 b”（a > b）时，没有任何方案可能满足。此时 `ConditionsOutcome.status='conflict'`，**资格判断整体暂停**（不产出任何 eligible/conditional/excluded 分组，待解决清单也留空，避免给出半套判断），冲突对在结果页顶部列出；原始评分照常计算展示，建议用户修改条件后重算。
2. **配置非法（输入期校验）**：阈值超出指标取值域、负容忍带等，由 `validateDraft` 在计算前拦截；阈值越界也同时在分析期以冲突形式报告，保证直接调用核心函数时不静默放行。

条件冲突不尝试“自动猜一个”，因为无论放宽哪一条都是价值取舍，必须由用户决定。

## 5. 与评分、推荐的衔接（一致策略）

分析结果中 `options` 仍按原始总分升序排列，每个方案挂自己的 `eligibility`；推荐状态机 `recommendationKind`：

| 情形 | 状态 | 行为 |
| --- | --- | --- |
| 未启用条件 | `unconstrained-winner / -tie` | **与改造前完全一致**：总分最低者胜出；前两名差 <5 分则不分胜负 |
| 条件冲突 | `condition-conflict` | 不推荐；列冲突；分数可见 |
| 有合格者，前两名（合格者内）差 ≥5 | `winner` | 合格者中总分最低者成为建议；文案说明其他方案即使总分相近也无资格 |
| 合格者前两名差 <5 | `tie` | 只在合格者集合内比较，不分胜负，建议补充信息 |
| 无合格者、有条件候选 | `conditional-only` | **不推荐**，列条件候选与“需要补哪些信息/核实哪些贴边数据” |
| 全部明确不满足 | `none-qualified` | **不选勉强胜者**，返回待解决条件：每个方案卡在哪条、差多少；提示可调事实或改/关条件后重算 |

关键规则：

- **原始分数始终计算、始终可见**（含未评估值处理，见下），资格只决定推荐资格；
- 未获资格方案在分数卡上打“不具备资格”印记并划线，但保留数字与逐条件原因，可展开查看；
- “接近不分胜负”只在合格者之间成立——被排除方案即使分数与胜者相同，也不触发平局。

### 5.1 未评估值在评分中的处理

评分规则不支持空洞：未评估（null）的影响值按**中性 0** 计入后悔分，同时在该方案上输出 `assumptions` 声明“此分基于中性假设”。门槛判断不使用该假设（仍为 unknown）。这样实现了“分数可见但不可用于取得资格”，且假设在报告中透明。

## 6. 重新计算、持久化与关闭

- 条件的任何增删改、开关、阈值/容忍带调整，与普通输入编辑一样把当前结果标记为**过期（stale）**，用户点击重新推演才重算——避免页面结论悄悄变化。
- 案例保存 `draft.conditions` 与 `analysis.conditions`（依据快照）；打印报告包含门槛清单、每方案资格与逐条件核对。
- **关闭整套条件**：`conditions.enabled=false` 时分析走原有分支，推荐与分数回到纯评分结果，条件配置保留不删除，可再次开启。
- 旧存档兼容：`normalizeDraft` 为缺少 `conditions` 的案例补 `{enabled:false}`，旧影响值缺键补 0、显式 null（新数据）保留；旧版分析结果无 `conditions` 依据，加载时不直接展示，标记过期并引导重新推演。

## 7. 直接排除 vs 保留为条件候选——适用范围速查

| 情况 | 处置 | 理由 |
| --- | --- | --- |
| 有事实、明确越过阈值（超出容忍带） | 直接排除 | 信息充分且违例明确，再讨论是浪费注意力 |
| 有事实、贴边（容忍带内） | 条件候选 | 测量/估计误差范围内，结论不稳定，先核实数据 |
| 无事实（未评估 null） | 条件候选 | 无知不是违例；排除会惩罚“还没调研”而非“不达标” |
| 条件自相矛盾/越界 | 暂停判断 | 问题在条件而非方案，先修条件 |
| 全部排除 | 返回待解决条件，无推荐 | 选“最不差的违规者”会让硬门槛失效 |
